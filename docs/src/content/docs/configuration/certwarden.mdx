**Cert Warden** is a centralized client ACME (Automated Certificate Management Environment), designed to simplify SSL/TLS certificate management. It is an open-source solution that provides an API for automating the acquisition, renewal, and distribution of certificates across different systems and services. Cert Warden is designed to simplify certificate management in complex infrastructures, where managing a large number of certificates for different domains or devices is required.

## How it works

<CertwardenDiagram lang="en" />

Cert Warden orders certificates from Let's Encrypt and proves domain ownership with a DNS-01 record at the DNS provider. It stores the issued certificates and serves them to clients via API keys: the client on each server polls Cert Warden every few hours, and when there is an update it downloads the pem files, writes them to disk and restarts its web server. A panel behind Caddy needs no file certificates at all: Caddy obtains them on its own.

## Why do we need Cert Warden?
Cert Warden solves the problem of automating certificate management in complex infrastructures, such as Kubernetes clusters, web applications, or IoT devices. Here are the main reasons why it can be useful:

1. **Automation:**
    - Cert Warden automates the acquisition, renewal, and distribution of SSL/TLS certificates, eliminating the need for manual management, which can be time-consuming and prone to errors.
    - Supports automatic renewal of certificates before their expiration date, minimizing the risk of downtime due to expired certificates.

2. **Centralized Management:**
    - Instead of configuring separate ACME clients on each server, Cert Warden allows managing all certificates from a single place. This is especially convenient in large infrastructures with multiple servers or domains.

3. **Security:**
    - Cert Warden uses API keys for client authentication, ensuring secure access to certificates.
    - Supports working with trusted certificate authorities, such as Let’s Encrypt, ensuring the use of valid and recognized certificates.

## Installation and configuration of Cert Warden

:::danger[Important]
We will install **Cert Warden** on the **Remnawave** panel server, but you can install it on any other server.
:::

:::danger[Important]
We will use the **dns-01 Cloudflare** method, but you can use other methods.
:::

<Steps>

1. Create a directory for Cert Warden and create `docker-compose.yml`

    ```bash
    mkdir /opt/certwarden && cd /opt/certwarden && nano docker-compose.yml
    ```

    Insert the following content:

    ```yaml title="docker-compose.yml"
    services:
      certwarden:
        container_name: certwarden
        image: ghcr.io/gregtwallace/certwarden:latest
        restart: unless-stopped
        ports:
          - '127.0.0.1:4050:4050'
        volumes:
          - ./certwarden-data:/app/data
        networks:
          - remnawave-network
        logging:
          driver: 'json-file'
          options:
            max-size: '30m'
            max-file: '5'

    networks:
      remnawave-network:
        name: remnawave-network
        driver: bridge
        external: true
    ```

2. Run Cert Warden

    ```bash
    cd /opt/certwarden && docker compose up -d && docker compose logs -f
    ```

3. Add Cert Warden to the panel web server so its interface is available on its own domain:

    <Tabs>
    <TabItem label="Nginx">

    ```bash
    cd /opt/remnawave && nano nginx.conf
    ```

    Add upstream section:

    ```nginx title="nginx.conf"
    upstream certwarden {
        server 127.0.0.1:4050;
    }
    ```

    Add server section:

    ```nginx title="nginx.conf" "yourdomain.com"
    server {
        listen 443 ssl;
        server_name certwarden.yourdomain.com; # Don't forget to add a DNS record in Cloudflare
        http2 on;

        ssl_certificate "/etc/nginx/ssl/yourdomain.com/fullchain.pem";
        ssl_certificate_key "/etc/nginx/ssl/yourdomain.com/privkey.pem";
        ssl_trusted_certificate "/etc/nginx/ssl/yourdomain.com/fullchain.pem";

        location / {
            proxy_pass http://certwarden;
            proxy_set_header Host $host;
            proxy_set_header X-Real-IP $remote_addr;
            proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
            proxy_set_header X-Forwarded-Proto $scheme;
        }
    }
    ```

    Restart nginx:

    ```bash
    cd /opt/remnawave && docker compose down remnawave-nginx && docker compose up -d remnawave-nginx
    ```

    </TabItem>
    <TabItem label="Caddy">

    ```bash
    cd /opt/remnawave && nano Caddyfile
    ```

    ```caddyfile title="Caddyfile" "yourdomain.com"
    certwarden.yourdomain.com {
        reverse_proxy 127.0.0.1:4050

    ```

    Caddy obtains the certificate for this domain on its own, just like for the panel.

    Restart Caddy:

    ```bash
    cd /opt/remnawave && docker compose restart remnawave-caddy
    ```

    </TabItem>
    </Tabs>

## Cert Warden Client

The Cert Warden client runs as a Docker container: it fetches certificates from the server using API keys, saves the files to disk and restarts the specified containers so the services pick up the update.

We use the [mishkatik/certwarden-client](https://github.com/mishkatik/certwarden-client) fork. With the [original client](https://github.com/gregtwallace/certwarden-client) the server pushes the certificate to the client, so the client keeps a port open and decrypts the payload with an AES key. In the fork the client polls the server itself: it opens no ports and needs no AES key.

- At startup and then every `CW_CLIENT_POLL_INTERVAL` (6 hours by default) the client makes one request to Cert Warden. If the certificate has not changed, the server answers with an empty `304` and nothing is downloaded.
- On the first start the client writes the files right away and restarts the containers.
- A renewed certificate is written within the configured time window (02:00 to 03:00 in the example below), and then the containers are restarted.
- If the server is unreachable or an API key is wrong, the client keeps running: it logs an error and retries after 15 minutes, doubling the pause after each failure until it reaches the poll interval.

:::note
The fork needs Cert Warden server 0.18.2 or newer. The `ghcr.io/gregtwallace/certwarden:latest` image from the guide above qualifies.
:::

:::tip[Panel behind Caddy]
If the panel runs behind Caddy, it needs no separate certificate files: Caddy obtains and renews them on its own. The Cert Warden client is then needed for the other services with file certificates, such as the nginx on nodes.
:::

:::caution[Moving from the old client]
If the client is already installed by the previous version of this guide (the `ghcr.io/gregtwallace/certwarden-client` image):

1. In Cert Warden, clear the client address and the `Client AES Key` under `Certificates` → `Post Processing` → `Client` of the certificate.
2. In `/opt/certwardenclient/docker-compose.yml`, change the image to `ghcr.io/mishkatik/certwarden-client:latest`, remove `ports` and the `CW_CLIENT_AES_KEY_BASE64` and `CW_CLIENT_KEY_NAME` variables.
3. Recreate the container: `cd /opt/certwardenclient && docker compose up -d`.

The fork understands the variables without an index (`CW_CLIENT_CERT_NAME` and the rest), so rewriting them to `CW_CLIENT_0_*` is optional.
:::

## Client on the Remnawave panel server

<Steps>

1. Check the certificate settings in Cert Warden: under `Certificates` → `Post Processing` → `Client`, the client address and the `Client AES Key` must be empty. The client fetches the certificate itself, there is nowhere to send it. If anything is filled in there, the server logs an error on every renewal.

2. Create a directory for the client:

    ```bash
    mkdir -p /opt/certwardenclient/certs && cd /opt/certwardenclient && nano docker-compose.yml
    ```

    Insert the following content:

    ```yaml title="docker-compose.yml" "https://certwarden.example.com" "example.com" "MkYMf7eXO8aB9xiNKqwvNVcDGKJ0Dg6v" "0UkmZEZK7oieQ6hmz9Fta2obMMZRjAuo"
    services:
        certwardenclient:
          image: ghcr.io/mishkatik/certwarden-client:latest
          container_name: certwardenclient
          restart: unless-stopped
          volumes:
            - /var/run/docker.sock:/var/run/docker.sock
            - /opt/certwardenclient/certs:/opt/certwarden/certs
          environment:
            TZ: "Europe/Moscow"
            CW_CLIENT_SERVER_ADDRESS: "https://certwarden.example.com"
            CW_CLIENT_POLL_INTERVAL: "6h"
            CW_CLIENT_0_CERT_NAME: "example.com"
            CW_CLIENT_0_CERT_APIKEY: "MkYMf7eXO8aB9xiNKqwvNVcDGKJ0Dg6v"
            CW_CLIENT_0_KEY_APIKEY: "0UkmZEZK7oieQ6hmz9Fta2obMMZRjAuo"
            CW_CLIENT_0_FILE_UPDATE_TIME_START: "02:00"
            CW_CLIENT_0_FILE_UPDATE_TIME_END: "03:00"
            CW_CLIENT_0_FILE_UPDATE_DAYS_OF_WEEK: "Mon Tue Wed Thu Fri Sat Sun"
            CW_CLIENT_0_RESTART_DOCKER_CONTAINER0: "remnawave-nginx"
            CW_CLIENT_0_CERT_PATH: "/opt/certwarden/certs"
            CW_CLIENT_0_KEY_PEM_FILENAME: "privkey.pem"
            CW_CLIENT_0_CERTCHAIN_PEM_FILENAME: "fullchain.pem"
          logging:
            driver: 'json-file'
            options:
              max-size: '30m'
              max-file: '5'
    ```

    `CW_CLIENT_0_RESTART_DOCKER_CONTAINER0` is set to `remnawave-nginx`. For a panel behind Caddy, use `remnawave-caddy`.

3. `CW_CLIENT_SERVER_ADDRESS` is the address of the Cert Warden server, for example `https://certwarden.example.com`. It must start with `https://`, otherwise the client does not start.

4. `CW_CLIENT_POLL_INTERVAL` sets how often to poll the server: `30m`, `6h`, `12h` and so on, but no more often than once a minute. The server logs every request, so a very short interval floods its log.

5. `CW_CLIENT_0_CERT_NAME` and `CW_CLIENT_0_CERT_APIKEY` are the name and the API key of the certificate from the `Certificates` section.

6. `CW_CLIENT_0_KEY_APIKEY` is the API key of the private key the certificate uses (the `Private Keys` section). If you switch the certificate to another key on the server, update this variable and restart the client.

7. `CW_CLIENT_0_FILE_UPDATE_TIME_START`, `CW_CLIENT_0_FILE_UPDATE_TIME_END` and `CW_CLIENT_0_FILE_UPDATE_DAYS_OF_WEEK` set the window in which the client writes a renewed certificate and restarts the containers. The time follows the `TZ` time zone, or UTC without it.

8. Run the client:

    ```bash
    cd /opt/certwardenclient && docker compose up -d && docker compose logs -f
    ```

9. The `fullchain.pem` and `privkey.pem` files should appear in the `/opt/certwardenclient/certs` folder.

10. Mount them in the panel's `docker-compose.yml`:

    ```bash
    cd /opt/remnawave && nano docker-compose.yml
    ```

    Add to volumes, do not forget to specify your domain:

    ```yaml title="docker-compose.yml" "yourdomain.com"
    volumes:
      - /opt/certwardenclient/certs/fullchain.pem:/etc/nginx/ssl/yourdomain.com/fullchain.pem
      - /opt/certwardenclient/certs/privkey.pem:/etc/nginx/ssl/yourdomain.com/privkey.pem
    ```

11. Restart nginx:

    ```bash
    cd /opt/remnawave && docker compose down remnawave-nginx && docker compose up -d remnawave-nginx
    ```

</Steps>

:::tip[Several certificates and containers]
Another certificate is added with a block of variables with index `1`: `CW_CLIENT_1_CERT_NAME`, `CW_CLIENT_1_CERT_APIKEY`, `CW_CLIENT_1_KEY_APIKEY` and so on. Give it its own file names (`CW_CLIENT_1_KEY_PEM_FILENAME`, `CW_CLIENT_1_CERTCHAIN_PEM_FILENAME`) so the certificates do not overwrite each other. Extra containers to restart go into `CW_CLIENT_0_RESTART_DOCKER_CONTAINER1`, `CW_CLIENT_0_RESTART_DOCKER_CONTAINER2` and so on, numbered without gaps.
:::

## Client on the Remnawave node server

:::note
The client is installed the same way on other nodes that will receive certificates from Cert Warden. You can do without it: on a node server the script itself can issue and renew certificates (item `11` "Manage certificates domain" → "Update current certificates"), and when a node is added through the menu, its certificates are deployed automatically. The Cert Warden client is only needed if you want to distribute all certificates from one place.
:::

<Steps>

1. Create a directory for the client:

    ```bash
    mkdir -p /opt/certwardenclient/certs && cd /opt/certwardenclient && nano docker-compose.yml
    ```

    Insert the following content:

    ```yaml title="docker-compose.yml" "https://certwarden.example.com" "example.com" "MkYMf7eXO8aB9xiNKqwvNVcDGKJ0Dg6v" "0UkmZEZK7oieQ6hmz9Fta2obMMZRjAuo"
        certwardenclient:
          image: ghcr.io/mishkatik/certwarden-client:latest
          container_name: certwardenclient
          restart: unless-stopped
          volumes:
            - /var/run/docker.sock:/var/run/docker.sock
            - /opt/certwardenclient/certs:/opt/certwarden/certs
          environment:
            TZ: "Europe/Moscow"
            CW_CLIENT_SERVER_ADDRESS: "https://certwarden.example.com"
            CW_CLIENT_POLL_INTERVAL: "6h"
            CW_CLIENT_0_CERT_NAME: "example.com"
            CW_CLIENT_0_CERT_APIKEY: "MkYMf7eXO8aB9xiNKqwvNVcDGKJ0Dg6v"
            CW_CLIENT_0_KEY_APIKEY: "0UkmZEZK7oieQ6hmz9Fta2obMMZRjAuo"
            CW_CLIENT_0_FILE_UPDATE_TIME_START: "02:00"
            CW_CLIENT_0_FILE_UPDATE_TIME_END: "03:00"
            CW_CLIENT_0_FILE_UPDATE_DAYS_OF_WEEK: "Mon Tue Wed Thu Fri Sat Sun"
            CW_CLIENT_0_RESTART_DOCKER_CONTAINER0: "remnawave-nginx"
            CW_CLIENT_0_CERT_PATH: "/opt/certwarden/certs"
            CW_CLIENT_0_KEY_PEM_FILENAME: "privkey.pem"
            CW_CLIENT_0_CERTCHAIN_PEM_FILENAME: "fullchain.pem"
          logging:
            driver: 'json-file'
            options:
              max-size: '30m'
              max-file: '5'
    ```

2. Fill in the variables the same way as on the panel server: `CW_CLIENT_SERVER_ADDRESS` is the address of the Cert Warden server, `CW_CLIENT_0_CERT_NAME` and `CW_CLIENT_0_CERT_APIKEY` come from the `Certificates` section, `CW_CLIENT_0_KEY_APIKEY` from the `Private Keys` section. If the node receives a different certificate, its `Post Processing` → `Client` must be empty too.

3. Run the client:

    ```bash
    cd /opt/certwardenclient && docker compose up -d && docker compose logs -f
    ```

4. The `fullchain.pem` and `privkey.pem` files should appear in the `/opt/certwardenclient/certs` folder.

5. Mount them in the node's `docker-compose.yml` (its web server is also called `remnawave-nginx`):

    ```bash
    cd /opt/remnanode && nano docker-compose.yml
    ```

    ```yaml title="docker-compose.yml" "yourdomain.com"
    volumes:
      - /opt/certwardenclient/certs/fullchain.pem:/etc/nginx/ssl/yourdomain.com/fullchain.pem
      - /opt/certwardenclient/certs/privkey.pem:/etc/nginx/ssl/yourdomain.com/privkey.pem
    ```

6. Restart the node's nginx:

    ```bash
    cd /opt/remnanode && docker compose down remnawave-nginx && docker compose up -d remnawave-nginx
    ```

</Steps>

## Closing access to Certwarden with Netbird

:::note
If you want to close access to Certwarden with Netbird, follow these steps
:::

<Steps>

1. Add the Cert Warden server to Netbird, as its installation can be seen [here](../netbird)

2. In the Cloudflare control panel for your domain certwarden.yourdomain.com, specify the IP address of the Cert Warden server in the Netbird network

      ![Cert Warden Cloudflare](https://raw.githubusercontent.com/eGamesAPI/remnawave-reverse-proxy/refs/heads/main/docs/src/assets/en/certwarden/certwarden_ip_netbird.png) 

3. Now, to access the Cert Warden page, you will need to connect to your network on your computer through the [Netbird](https://docs.netbird.io/how-to/installation) application
</Steps>

:::caution[Clients must be in the NetBird network too]
The Cert Warden client connects to the server by the `certwarden.yourdomain.com` domain itself. When the domain points to an IP in the NetBird network, every server running a client must be connected to NetBird too, otherwise the client cannot fetch the certificate.
:::
