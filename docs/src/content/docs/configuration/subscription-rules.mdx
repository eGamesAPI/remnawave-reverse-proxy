Response rules decide what the panel returns for every subscription request. A client app needs its configs, a browser deserves a nice page, and a stranger script walking through stolen links is best served a 404 and nothing else. The module shows the current state on one screen, applies ready-made rule sets and enables per-device subscription binding. Everything changes through the panel API, no configs are edited by hand.

## How it works

The panel evaluates every subscription request by its headers: which app sent it and from which device. A rule combines header conditions with a response type. Rules are checked top to bottom, the first match wins, and its response type goes to the client.

<SubscriptionRulesDiagram lang="en" />

Device binding works alongside the rules. Happ and INCY send an `x-hwid` header with the device identifier. When the limit is on, a user's subscription is served to at most N devices, the rest receive a polite message instead of configs. The list of occupied slots is visible in the user's card in the panel, a lost device can be removed there to free its slot. Individual users can have their own limit or none at all, that is done in the panel.

Everything is stored in the panel, the same settings are available in its web UI in the subscriptions section. The module is a convenience wrapper: it changes values through the API, shows the result and keeps copies. If you use the panel's external squads, keep in mind that response rules take priority over their settings.

:::note[Panel 3.4 and newer]
Recent panel versions answer 403 to subscription requests until rules are configured. If subscriptions suddenly stopped opening after a panel update, apply any rule set from this module and everything comes back.
:::

## What the panel can return

The response type in a rule decides what exactly the client receives. The module's rule sets use some of the types, custom rules in the panel can be built from the full list.

| Response type | What the client receives |
|---|---|
| Xray JSON | The complete Xray config as one file, with routing rules. This is how Happ, INCY and v2rayN work |
| Base64 | The plain server list Base64-encoded. Every app understands it, a safe default choice |
| Mihomo, Clash, Stash, Sing-box | A config in the format of that client family |
| Browser page | The subscription HTML page with the server list and instructions |
| Block 403, 404, 451 | An empty refusal. For stranger requests 404 looks the most natural: as if nothing ever lived at this address |
| Socket drop | The panel silently drops the connection, without a status code |

## Strict preset

The “Strict: Happ and INCY + devices” preset is built for selling subscriptions. It hands configs only to verified requests and returns 404 to everything else. The rule set looks like this:

| Who asks | Condition | What they receive |
|---|---|---|
| Happ, INCY and RenoarX | `user-agent` starts with `Happ/`, `INCY/` or `RenoarX/`, a valid `x-hwid` is present | The complete Xray JSON config |
| Clash clients | `user-agent` starts with `FlClashX/`, `koala-clash/`, `prizrak-box/`, `rabbithole/`, `clash-mi/`, `Flowvy/` or `ClodClash/`, a valid `x-hwid` is present | The Mihomo config for their Clash core |
| Sing-box clients | `user-agent` starts with `Karing/`, `InHive/`, `Throne/` or `DeskBox/`, a valid `x-hwid` is present | The Sing-box config |
| Known apps | `user-agent` starts with a name from the list: v2rayN, v2rayNG, v2RayTun, V2Box, Streisand, Shadowrocket, sing-box, Karing, FlClash, Flowvy, prizrak-box, Koala Clash, Clod Clash, RenoarX, Throne, DeskBox, sfa, sfi, sfm, sft, rabbithole | The Base64 list |
| Browser | `user-agent` contains Mozilla | The subscription page |
| Everyone else | no conditions | 404 |

The strict preset makes sense together with the device limit: a stolen link then stays useless even with a faked app name, because the stranger device will not pass the limit. Clash and Sing-box clients, RenoarX, Happ and INCY report the device identifier to the panel: with the limit on they pass the check and receive the config in their own format.

:::danger[Important]
After the strict preset, apps outside the list, for example Hiddify, Clash Verge or NekoBox, will receive 404. Check the subscription on your own device right away. Not a fit: switch back to “Clients and browsers” or restore a saved copy.
:::

## Device limit

Enabled by item 5. The panel asks how many devices per user are allowed and shows a warning:

What the panel knows about a device:

| Header | What it carries | Example |
|---|---|---|
| `x-hwid` | The device identifier, required for the limit | `UE42LJXu4DbiCaBv` |
| `x-device-os` | The device system | `iOS` or `Android` |
| `x-ver-os` | The system version | `18.3` |
| `x-device-model` | The device model | `iPhone 14 Pro Max` |

Happ, INCY, RenoarX, DeskBox, v2RayTun, Flowvy, Clod Clash and the Clash clients send these headers on their own. Throne, Shadowrocket, Clash Mi and Karing support the binding too, but send the header only after it is enabled in the app settings. Left without the header are v2rayN, v2rayNG, FlClash, Stash and the official sing-box apps: with the limit on, their users will not receive the subscription. Such a user gets the limit disabled individually in their panel card, the restriction keeps working for everyone else.

The limit counts distinct devices. When a user changes phones and the old one holds a slot, the extra device is removed from the card list and the new one passes right away.

## Restoring
