The client balancer gives users one entry in the subscription that always works well. When one of the hosts gets weak or goes down, there is nothing to reconfigure: the client measures the latency of every host and keeps traffic on the two best ones. The panel assembles this config automatically, nothing changes on the nodes, and the original hosts are not deleted. While the balancer lives they are hidden from the subscription: dead entries would only confuse users. Removing the balancer brings back both the nodes and the entries.

## Presets

<Tabs>
  <TabItem label="Always the fastest">

  One pool, every host equal. The balancer spreads connections across the two best hosts by measured latency (`leastLoad`, `expected: 2`). Fit for a set of similar servers where any of them is a fine choice.

  <PresetDiagram variant="fastest" lang="en" />

  </TabItem>
  <TabItem label="Main with backup">

  Two groups. Traffic goes through the main hosts; when all of them are unreachable, the client falls back to the first backup host. Fit for a main line abroad plus one entry that survives regional blocks: the backup sits idle until it is actually needed.

  <PresetDiagram variant="reserve" lang="en" />

  Xray balancers cannot chain into each other (`fallbackTag` names an outbound), so the fallback is the first host of the backup group. Reorder by removing and re-adding hosts when a different one should be first.

  Picking every host as a main is not allowed: the wizard keeps at least one host for the reserve and warns when fewer than two eligible hosts leave no room for two groups.

  The client re-probes the pool every 30 seconds, so switching to the reserve fits into one probe. Connections that were already riding the dead host live until their own timeout.

  </TabItem>
</Tabs>

Hosts that already carry a job of their own are never offered to a balancer: VLESS Route hosts of the server routing module (they are personal exits, and the routing module may rewire them) and wrappers of other balancers.

## Several balancers

There can be as many balancers as you need, each with its own host list, its own Xray JSON template and its own entry in the subscription. Five nodes of Germany gather into a balancer "Germany", five nodes of Finland into another "Finland", and the user sees both entries under different names.

With a cross-inbound build each one gets its own profile: the first takes "Balancer", the second automatically "Balancer 2", and so on. Tearing one down never touches the other, and wrappers of neighbouring balancers never appear in the host picker, so an accidental duplicate record is impossible.

## The balancer and server routing

The modules work together because they answer different questions: the balancer on the client picks the entry point, server routing after the entry decides where traffic goes. Russian domains travel through the bridge to the exit server, everything else leaves the entry node directly.

### A uniform pool

Build a pool of nodes with the same routing and nothing breaks: the nodes stay on their own profiles with their own rules, and the balancer simply picks the fastest among them. No dedicated profile is even created.

<RoutingComboDiagram variant="alike" lang="en" />

### A mixed pool

Do not gather nodes with and without routing "Across inbounds". The dedicated profile inherits the rules of the first picked host, including the reference to the RU list file, and that file is not mounted on every node: a node without it cannot load the config and drops from the panel. Once the balancer is torn down, the node comes back on its own. Personal VLESS Route exits never join a pool at all: server routing may rewire them, so the module never offers them.
