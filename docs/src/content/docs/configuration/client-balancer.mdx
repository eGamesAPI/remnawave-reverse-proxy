The client balancer gives users one entry in the subscription that always works well. When one of the hosts gets weak or goes down, there is nothing to reconfigure: the client measures the latency of every host and keeps traffic on the two best ones. The panel assembles this config automatically, nothing changes on the nodes, and the original hosts are not deleted: they keep working. While the balancer lives they are hidden from the subscription, so the extra list never gets in the user's way. Removing the balancer puts the entries back, so you can safely try it on a live panel.

## Presets

<Tabs>
  <TabItem label="Always the fastest">

  One pool, every host equal. The balancer spreads connections across the two best hosts by measured latency (`leastLoad`, `expected: 2`). Fit for a set of similar servers where any of them is a fine choice.

  <PresetDiagram variant="fastest" lang="en" />

  </TabItem>
  <TabItem label="Main with backup">

  Two groups. Traffic goes through the main hosts; when all of them are unreachable, the client falls back to the first backup host. Fit for a main line abroad plus a spare entry on another territory: the backup sits idle until it is actually needed.

  <PresetDiagram variant="reserve" lang="en" />

  Xray balancers cannot chain into each other (`fallbackTag` names an outbound), so the fallback is the first host of the backup group. Reorder by removing and re-adding hosts when a different one should be first.

  Picking every host as a main is not allowed: the wizard keeps at least one host for the reserve and warns when fewer than two eligible hosts leave no room for two groups.

  The client re-probes the pool every 30 seconds, so switching to the reserve fits into one probe. Connections that were already riding the dead host live until their own timeout.

  </TabItem>
</Tabs>

Only copies and wrappers of other balancers stay out of the list: the module hides them on its own. Hosts with a personal VLESS Route (bridges) can be picked freely: the copy keeps the route, and the connection goes through the bridge entry as usual. Disabled hosts are never offered, hidden ones are marked in the list.

## Several balancers

There can be as many balancers as you need, each with its own host list, its own Xray JSON template and its own entry in the subscription. Five nodes of Germany gather into a balancer "Germany", five nodes of Finland into another "Finland", and the user sees both entries under different names.

Tearing one down never touches the other, and copies and wrappers of neighbouring balancers never appear in the host picker, so an accidental duplicate record is impossible.

## The balancer and server routing

The modules work together because they answer different questions: the balancer on the client picks the entry point, server routing after the entry decides where traffic goes. Russian domains travel through the bridge to the exit server, everything else leaves the entry node directly.

<RoutingComboDiagram variant="alike" lang="en" />

Every hidden copy in the config points at its own node and its rules keep working as configured, so a pool may mix anything: nodes with and without routing, direct entries and bridges, different transports. No shared profile is created, the rules of one node are never carried anywhere, and nodes are never switched. A bridge host (a VLESS Route record) joins the pool with its route intact: the client connects to the bridge entry, and traffic then travels through the exit server as usual.

:::note[Verified on a live panel]
The scheme with a direct entry, a VLESS Route bridge and an XHTTP entry on its own inbound was run end to end: the pool was built from all three, the backup carried the XHTTP transport with its own keys and port, the bridge kept its route in the config (the marker inside the user id), and the teardown left nothing behind: nodes, profiles, user squads and hosts returned to their original shape.
:::
