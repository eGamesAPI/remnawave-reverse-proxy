The SSH access module lets you service a second server (for example, the node server) right from the script menu on the panel: update packages, restart the node container, read logs, without opening a second SSH session. Another module, [server routing](/configuration/server-routing/), uses this access automatically when it installs a node on the second server.

- **The password is asked once.** The script installs its own key and forgets the password: it is never written to disk.
- **Your key is never read.** An existing key is used in place; its contents are not copied or opened.
- **One line in `authorized_keys`.** The script's key lives on its own line marked `remnawave-reverse-proxy`; your lines are untouched.

The menu item lives at **4. Node extensions → SSH access to remote servers**.

## First-time setup

<Steps>

1. **Pick the server address.** The script first asks for the address by hand, and if the panel already knows nodes, it shows them as a list to pick a ready address:

    <Terminal title="root@server: ~" lines={[
      { kind: 'plain', text: 'Server address (IP or domain): ', answer: '203.0.113.20' },
      { kind: 'plain' },
      { kind: 'title', text: 'Nodes known to the panel' },
      { kind: 'plain' },
      { kind: 'item', num: '1.', text: 'node.example.com ', warn: '(node-kazan)' },
      { kind: 'item', num: '2.', text: 'Enter an address manually' },
    ]} />

2. **Port, user and label.** Port and user can be left at the defaults: Enter fills in `22` and `root`. The label is the server's name in the list:

    <Terminal title="root@server: ~" lines={[
      { kind: 'plain', text: 'SSH port (Enter — 22): ', answer: '22' },
      { kind: 'plain', text: 'SSH user (Enter — root): ', answer: 'root' },
      { kind: 'plain', text: 'Server label in the SSH connections list (Enter — no label): ', answer: 'Kazan' },
    ]} />

3. **Probing existing keys.** If this server already holds a key that opens the second server, the script takes it silently: no questions, nothing changed on the remote side. If no key works, it offers three paths:

    <Terminal title="root@server: ~" lines={[
      { kind: 'step', text: 'Trying keys already present on this server...' },
      { kind: 'err', text: 'No existing key works for that server' },
      { kind: 'plain' },
      { kind: 'title', text: 'No key worked — choose how to proceed' },
      { kind: 'plain' },
      { kind: 'item', num: '1.', text: 'Point at an existing key on this server' },
      { kind: 'dim', text: '   the file is used in place, its contents are never read' },
      { kind: 'item', num: '2.', text: 'Enter the root password once' },
      { kind: 'dim', text: '   only used to install our own key, then discarded' },
      { kind: 'item', num: '3.', text: 'Show our public key for manual setup' },
      { kind: 'dim', text: '   for servers with password login disabled' },
      { kind: 'plain' },
      { kind: 'input', text: 'Select action (1-3):' },
    ]} />

    - **Your own key**: point at its path, the file is used in place.
    - **Root password once**: the script asks for the password (hidden input), installs its own separate key and forgets it.
    - **Manual paste**: for servers with password login disabled, the script shows its public key and the command to run on the second server. The check repeats on <Kbd windows="Enter" />, waiting exits with <Kbd windows="Q" />.

4. **Installing the key with a password** looks like this:

    <Terminal title="root@server: ~" lines={[
      { kind: 'plain', text: 'Root password of 203.0.113.20 (input hidden): ' },
      { kind: 'step', text: 'Installing our key on 203.0.113.20...' },
      { kind: 'ok', text: 'Key installed — the password is no longer needed' },
      { kind: 'plain' },
      { kind: 'ok', text: 'Access saved: root@203.0.113.20:22' },
    ]} />

</Steps>

:::tip[Check after setup]
The module offers to test the connection right away and show the remote server's hostname:

<Terminal title="root@server: ~" lines={[
  { kind: 'ok', text: 'Connection works (remote host: node-kazan)' },
]} />

If you see it, access works.
:::

:::note[If the server was reinstalled]
On a host key mismatch the script never connects silently: it shows the fingerprint the server presents and asks for confirmation:

<Terminal title="root@server: ~" lines={[
  { kind: 'err', text: 'The host key of 203.0.113.20:22 differs from the one saved in known_hosts: the server was reinstalled or the address now belongs to another server' },
  { kind: 'step', text: 'The server presents key ED25519 SHA256:9Xk…, verify it against the output on the server itself:' },
  { kind: 'dim', text: '  ssh-keygen -l -f /etc/ssh/ssh_host_ed25519_key.pub' },
  { kind: 'plain' },
  { kind: 'input', text: 'Forget the old host key and reconnect? (y/n): ', answer: 'y' },
]} />
:::

## Running commands

The `Run a command` item executes a command on the remote server, the output lands in your terminal, and the script prints the exit code at the end:

<Terminal title="root@server: ~" lines={[
  { kind: 'plain', text: 'Command to run on root@203.0.113.20:22: ', answer: 'docker logs remnanode --tail 5' },
  { kind: 'dim', text: '… command output …' },
  { kind: 'ok', text: 'Command finished (exit code 0)' },
  { kind: 'dim', text: 'Enter returns to the menu...' },
]} />

Typical scenarios:

```bash title="Update packages on the remote server"
apt update && apt upgrade -y
```

```bash title="Update the node (commands start in /root, compose needs cd)"
cd /opt/remnanode && docker compose pull && docker compose up -d
```

```bash title="Node logs"
docker logs remnanode --tail 50
```

:::note[Limitations]
Interactive programs (`top`, `nano`, `mc`) will not work: no terminal is allocated on the remote side. To check status, use plain commands with text output: `docker logs`, `free -h`, `df -h`.
:::

<details>
<summary><strong>Under the hood: where it is stored</strong></summary>

All access data lives on the panel in `/usr/local/remnawave_reverse`:

<FileTree>
- /usr/local/remnawave_reverse
  - remote-exec
    - **203.0.113.20_22.target** (server: address, port, user, key, label)
    - 203.0.113.5_22.target
  - remote-exec.active (which server was used last)
  - ssh
    - id_ed25519 (the script's key, one for all servers)
    - known_hosts
</FileTree>

The `.target` files are plain `key=value`; edit them by hand only as a last resort: the rename and reconfigure menus do the same thing safely.

</details>
