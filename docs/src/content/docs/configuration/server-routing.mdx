Server routing ties two of your servers together so user traffic splits by direction: some sites open straight from the entry node, the rest travel a tunnel to the exit server. Users notice nothing: same subscription, same addresses, same entry speed.

- **Two directions.** Russian and foreign sites see different IPs, and you choose which side sees which address.
- **Shadowsocks transport.** One `chacha20-ietf-poly1305` tunnel between the servers, all traffic including UDP.
- **Everything through the panel.** Profiles, squads and the service user are created automatically via the API.
- **No node needed in advance.** The script installs it over SSH itself, together with Docker and the ufw port.
- **A second bridge type: VLESS Route.** Every user picks their own exit: the profile gets an extra host in the subscription.

You need a panel on this server and a second server.

:::danger[Important]
The squad the script creates for the bridge is a service one: it has no hosts and its subscription is empty. Regular squads with the entry node are for users; routing rules live in the server-side config and apply to everyone passing through the node.
:::

## How it works

<BridgeDiagram lang="en" />

The module moves service traffic into a private network without breaking anything on the public path: an outbound Shadowsocks and rules are added to the entry node's profile config, saying where Russian traffic goes and what stays direct. On the exit server a node comes up with a single service inbound: it serves nothing to users, it only terminates the tunnel.

<details>
<summary><strong>Under the hood: rules in the profile</strong></summary>

In "Through the bridge" mode the profile config gets an outbound and these rules:

```json
{ "ip": ["geoip:private"], "outboundTag": "BLOCK" },
{ "protocol": ["bittorrent"], "outboundTag": "BLOCK" },
{ "ip": ["geoip:ru"], "outboundTag": "SR_BRIDGE_SS" },
{ "domain": ["geosite:category-ru"], "outboundTag": "SR_BRIDGE_SS" }
```

In "Straight from the entry node" mode `geoip:ru` and `geosite:category-ru` switch their `outboundTag` to `DIRECT`, and a catch-all rule is added: all remaining profile traffic goes to `SR_BRIDGE_SS`. With extended RU lists one more rule with `ext:geosite-ruex.dat:ru-available-only-inside` is appended, always assigned to the bridge.

</details>

## Bridge via VLESS Route

The country bridge decides for everyone: one direction per profile. The second type hands the choice to the user. The profile gets an extra host in the subscription, for example "Germany → Moscow", and selecting it sends all of that user's traffic through the bridge server: both Russian and foreign sites see its IP. The regular host keeps working as before.

| Subscription host | RU sites see | Foreign sites see |
|---|---|---|
| Germany (regular) | by the profile's common rules | by the profile's common rules |
| Germany → Moscow | bridge server IP | bridge server IP |

Hosts switch in the client any time, without a reinstall or a second subscription: a phone can live on "Germany → Moscow" for the banks while the computer stays on plain "Germany".

### How it is built

<BridgeDiagram variant="route" lang="en" />

The route number is a native host field in the panel (`vlessRouteId`). The panel bakes the number into the link UUID, the entry node reads it and sends the connection through the right outbound. The user configures nothing: they just pick a host with a clear name.

- **A line per exit.** As many lines as exit servers, each with its own route number and its own statistics on the service user in the panel.
- **Exit reuse.** A second line to the same exit needs no new server: same tunnel, own service user, own traffic accounting.
- **Several entries.** The `Attach another profile` item adds a host "its entry → this exit" on the second entry node under the same route number.
- **Geo does not interfere.** Route rules sit above geo rules: an assigned user goes to their exit entirely, the rest live by the common rules.

<details>
<summary><strong>Under the hood: rules and UUID</strong></summary>

The entry node's profile gets an outbound and rules with route numbers:

```json
{ "vlessRoute": 1, "outboundTag": "DIRECT" },
{ "vlessRoute": 2, "outboundTag": "SR_BRIDGE_SS_kazan" }
```

Route 1 is service traffic: direct egress from the entry node; a host for it is created only if the profile is already country-split. The number lives in the third UUID group: user `9d5f42a1-7b3c-4d8e-…` on route 2 gets a link with `9d5f42a1-7b3c-0002-…`, and that pair of bytes is what the node reads as the number.

</details>

## Extended RU lists

The stock `geosite:category-ru` rule covers all domains in `.ru`, `.su`, `.рф` plus name lists. But Russian services living on foreign domains never make it in and stay behind.

The `RU lists` item connects the daily-updated lists from the [runetfreedom](https://github.com/runetfreedom/russia-v2ray-rules-dat) project. One rule is added for domains reachable only from inside Russia (`ext:ru-available-only-inside`):

<Terminal title="root@server: ~" lines={[
  { kind: 'input', text: 'Enable the extended RU lists (domains reachable only from inside RU)? Stock rules stay, one ext: rule is added (y/n): ', answer: 'y' },
  { kind: 'step', text: 'Downloading geosite.dat from runetfreedom...' },
  { kind: 'ok', text: 'File fetched, checksum matches' },
  { kind: 'step', text: 'Mounting the lists into node node.example.com...' },
  { kind: 'step', text: 'Adding the ext:ru-available-only-inside rule to bridged profiles...' },
  { kind: 'ok', text: 'Rule added, profiles updated: 1' },
  { kind: 'ok', text: 'Extended RU lists enabled on: node.example.com' },
]} />

- **Nothing is replaced.** Stock rules stay as they are; the new rule is added on top.
- **Always a Russian exit.** Domains on the list get an RU egress in every bridge mode.
- **Installed on entry nodes.** The entry node makes the routing decisions, so the list file lands there, separate from Xray's stock geodata.
- **Self-updating.** Every day at 4:30 a fresh copy is downloaded from mirrors and checksum-verified. Nodes restart only when the file actually changed.

<details>
<summary><strong>Under the hood: files and cron</strong></summary>

<FileTree>
- /usr/local/remnawave_reverse
  - server-routing
    - **kazan.bridge** (bridge: server, port, mode, panel objects)
    - ruex.state (extended lists state)
    - ruex-update.sh (daily updater)
    - ruex-update.log (last 50 log lines)
</FileTree>

The `crontab -l` line looks like: `30 4 * * * bash /usr/local/remnawave_reverse/server-routing/ruex-update.sh`. The updater downloads the dat file from four mirrors, checks sha256 and spreads it over the entry nodes; node restarts go through the panel API and only on a real file change.

</details>

## Removing

`Remove routing` returns profiles to direct egress, deletes the service user and the squad, and closes the ufw port on the second server. The bridge node and profile stay: they no longer route anything, and you can delete them in the panel by hand if they are not needed.
