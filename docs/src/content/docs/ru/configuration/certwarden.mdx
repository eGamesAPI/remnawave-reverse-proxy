**Cert Warden** хранит SSL-сертификаты в одном месте и раздаёт их серверам: сам получает и продлевает их по ACME (Let's Encrypt), а клиенты забирают файлы по API-ключам и перезапускают свои сервисы. Это удобно, когда доменов и серверов много: за все сертификаты отвечает один сервер, certbot на каждом не нужен.

## Как это работает

<CertwardenDiagram lang="ru" />

Cert Warden заказывает сертификаты у Let's Encrypt и доказывает владение доменом DNS-01-записью у DNS-провайдера. Готовые сертификаты он хранит у себя и раздаёт клиентам по API-ключам: клиент на каждом сервере сам раз в несколько часов опрашивает Cert Warden, при обновлении скачивает pem-файлы, кладёт их на диск и перезапускает свой веб-сервер. Панели за Caddy файловые сертификаты не нужны: Caddy получает их сам.

## Установка Cert Warden

:::danger[Важно]
Устанавливать **Cert Warden** будем на сервер панели **Remnawave**, но вы можете установить его на любой другой сервер. Владение доменом проверяем методом DNS-01: ниже разобраны Cloudflare, Gcore и Bunny.net.
:::

<Steps>

1. Создаём директорию для Cert Warden и файл `docker-compose.yml`:

    ```bash
    mkdir /opt/certwarden && cd /opt/certwarden && nano docker-compose.yml
    ```

    Вставляем следующее содержимое:

    ```yaml title="docker-compose.yml"
    services:
      certwarden:
        container_name: certwarden
        image: ghcr.io/gregtwallace/certwarden:latest
        restart: unless-stopped
        ports:
          - '127.0.0.1:4050:4050'
        volumes:
          - ./certwarden-data:/app/data
        networks:
          - remnawave-network
        logging:
          driver: 'json-file'
          options:
            max-size: '30m'
            max-file: '5'

    networks:
      remnawave-network:
        name: remnawave-network
        driver: bridge
        external: true
    ```

2. Запускаем Cert Warden:

    ```bash
    cd /opt/certwarden && docker compose up -d && docker compose logs -f
    ```

3. Добавляем Cert Warden в веб-сервер панели, чтобы его интерфейс был доступен по своему домену:

    <Tabs>
    <TabItem label="Nginx">

    ```bash
    cd /opt/remnawave && nano nginx.conf
    ```

    Добавляем секцию upstream:

    ```nginx title="nginx.conf"
    upstream certwarden {
        server 127.0.0.1:4050;
    }
    ```

    Добавляем секцию server:

    ```nginx title="nginx.conf" "yourdomain.com"
    server {
        listen 443 ssl;
        server_name certwarden.yourdomain.com; # Не забудьте добавить запись DNS в Cloudflare
        http2 on;

        ssl_certificate "/etc/nginx/ssl/yourdomain.com/fullchain.pem";
        ssl_certificate_key "/etc/nginx/ssl/yourdomain.com/privkey.pem";
        ssl_trusted_certificate "/etc/nginx/ssl/yourdomain.com/fullchain.pem";

        location / {
            proxy_pass http://certwarden;
            proxy_set_header Host $host;
            proxy_set_header X-Real-IP $remote_addr;
            proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
            proxy_set_header X-Forwarded-Proto $scheme;
        }
    }
    ```

    Перезапускаем nginx:

    ```bash
    cd /opt/remnawave && docker compose down remnawave-nginx && docker compose up -d remnawave-nginx
    ```

    </TabItem>
    <TabItem label="Caddy">

    ```bash
    cd /opt/remnawave && nano Caddyfile
    ```

    Добавляем в конец файла сайт Cert Warden:

    ```caddyfile title="Caddyfile" "yourdomain.com"
    certwarden.yourdomain.com {
        reverse_proxy 127.0.0.1:4050
    }
    ```

    Сертификат на этот домен Caddy получит сам, как и для панели.

    Перезапускаем Caddy:

    ```bash
    cd /opt/remnawave && docker compose restart remnawave-caddy
    ```

    </TabItem>
    </Tabs>

4. Открываем браузер и переходим по ссылке:

    :::danger[Важно]
    Не забываем добавить запись DNS для вашего домена у провайдера DNS.
    :::

    ```bash "yourdomain.com"
    https://certwarden.yourdomain.com
    ```

5. Входим в систему, используя логин `admin` и пароль `password`:

    <div style={{ display: 'flex', justifyContent: 'center' }}>
      <img
        src="https://raw.githubusercontent.com/eGamesAPI/remnawave-reverse-proxy/refs/heads/main/docs/src/assets/en/certwarden/certwarden_login.png"
        alt="Cert Warden Login"
        style={{ maxWidth: '50%' }}
      />
    </div>

6. Попадаем на главную страницу:

    ![Cert Warden dashboard](https://raw.githubusercontent.com/eGamesAPI/remnawave-reverse-proxy/refs/heads/main/docs/src/assets/en/certwarden/certwarden_dashboard.png)

7. Переходим в раздел `Settings` и меняем текущий пароль.

</Steps>

## Настройка Provider

Провайдер отвечает за DNS-записи при проверке домена. У Cloudflare в Cert Warden есть нативный провайдер, Gcore и Bunny.net подключаются через встроенный движок lego.

<Tabs>
<TabItem label="Cloudflare">

<Steps>

1. Переходим в раздел `Providers` и нажимаем `New Provider`.

2. Выбираем `DNS-01 Cloudflare`.

3. В поле `Domains` вводим домен, для которого будем получать wildcard-сертификаты.

4. В поле `API Access Method` выбираем `API Token`. Инструкцию по созданию токена с правами `Zone:Edit` можно найти в [официальной документации Cloudflare](https://developers.cloudflare.com/fundamentals/api/get-started/create-token/).

        style={{ maxWidth: '60%' }}
      />
    </div>

5. Нажимаем `Submit`.

</Steps>

</TabItem>
<TabItem label="Gcore">

<Steps>

1. Переходим в раздел `Providers` и нажимаем `New Provider`.

2. Выбираем `DNS-01 go-acme (le-go)`.

3. В поле `Domains` вводим домен, для которого будем получать wildcard-сертификаты (например, `*.example.com`).

4. В поле `Code` вводим код провайдера: `gcore`.

5. В поле `Environment Variables` добавляем постоянный API-токен из панели Gcore в формате `ИМЯ=ЗНАЧЕНИЕ`, без слова `export`:

    ```text "GCORE_PERMANENT_API_TOKEN"

    ```

6. Нажимаем `Submit`.

</Steps>

</TabItem>
<TabItem label="Bunny.net">

<Steps>

1. Переходим в раздел `Providers` и нажимаем `New Provider`.

2. Выбираем `DNS-01 go-acme (le-go)`.

3. В поле `Domains` вводим домен, для которого будем получать wildcard-сертификаты (например, `*.example.com`).

4. В поле `Code` вводим код провайдера: `bunny`.

5. В поле `Environment Variables` добавляем Access Key из аккаунта bunny.net в формате `ИМЯ=ЗНАЧЕНИЕ`, без слова `export`:

    ```text "BUNNY_API_KEY"
    BUNNY_API_KEY=ваш_ключ
    ```

6. Нажимаем `Submit`.

</Steps>

</TabItem>
</Tabs>

Полный список кодов провайдеров и их переменных приведён в [документации lego](https://go-acme.github.io/lego/dns/). Cert Warden перенаправляет переменные в lego как есть.
:::

## Cert Warden Client

Клиент Cert Warden работает как Docker-контейнер: забирает сертификаты с сервера по API-ключам, сохраняет файлы на диск и перезапускает указанные контейнеры, чтобы сервисы подхватили обновление.

Используем форк [mishkatik/certwarden-client](https://github.com/mishkatik/certwarden-client). В [оригинальном клиенте](https://github.com/gregtwallace/certwarden-client) сертификат клиенту отправляет сам сервер, поэтому клиент держит открытый порт и расшифровывает данные AES-ключом. В форке клиент сам опрашивает сервер: портов он не открывает, AES-ключ не нужен.

- При запуске и затем раз в `CW_CLIENT_POLL_INTERVAL` (по умолчанию 6 часов) клиент делает один запрос к Cert Warden. Если сертификат не менялся, сервер отвечает пустым `304`, и ничего не скачивается.
- При первом запуске клиент сразу записывает файлы и перезапускает контейнеры.
- Продлённый сертификат клиент записывает в заданное окно времени (в примере ниже с 02:00 до 03:00) и после этого перезапускает контейнеры.
- Если сервер недоступен или API-ключ неверный, клиент не останавливается: пишет ошибку в лог и повторяет попытку через 15 минут, удваивая паузу после каждой неудачи, пока она не сравняется с интервалом опроса.

:::note
Форку нужен сервер Cert Warden версии 0.18.2 или новее. Образ `ghcr.io/gregtwallace/certwarden:latest` из инструкции выше подходит.
:::

:::tip[Панель за Caddy]
Если панель стоит за Caddy, отдельные файлы сертификатов ей не нужны: Caddy получает и продлевает их сам. Клиент Cert Warden тогда нужен остальным сервисам с файловыми сертификатами, например nginx нод.
:::

:::caution[Переход со старого клиента]
Если клиент уже стоит по прежней версии этой инструкции (образ `ghcr.io/gregtwallace/certwarden-client`):

1. В Cert Warden у сертификата в `Certificates` → `Post Processing` → `Client` очистите адрес клиента и `Client AES Key`.
2. В `/opt/certwardenclient/docker-compose.yml` смените образ на `ghcr.io/mishkatik/certwarden-client:latest`, удалите `ports` и переменные `CW_CLIENT_AES_KEY_BASE64` и `CW_CLIENT_KEY_NAME`.
3. Пересоздайте контейнер: `cd /opt/certwardenclient && docker compose up -d`.

Переменные без индекса (`CW_CLIENT_CERT_NAME` и другие) форк понимает, переписывать их на `CW_CLIENT_0_*` не обязательно.
:::

## Клиент на сервере панели Remnawave

<Steps>

1. Проверяем настройки сертификата в Cert Warden: в разделе `Certificates` → `Post Processing` → `Client` адрес клиента и `Client AES Key` должны быть пустыми. Клиент сам забирает сертификат, отправлять его некуда. Если там что-то заполнено, сервер будет писать ошибку при каждом продлении.

2. Создаём директорию для клиента:

    ```bash
    mkdir -p /opt/certwardenclient/certs && cd /opt/certwardenclient && nano docker-compose.yml
    ```

    Вставляем следующее содержимое:

    ```yaml title="docker-compose.yml" "https://certwarden.example.com" "example.com" "MkYMf7eXO8aB9xiNKqwvNVcDGKJ0Dg6v" "0UkmZEZK7oieQ6hmz9Fta2obMMZRjAuo"
    services:
        certwardenclient:
          image: ghcr.io/mishkatik/certwarden-client:latest
          container_name: certwardenclient
          restart: unless-stopped
          volumes:
            - /var/run/docker.sock:/var/run/docker.sock
            - /opt/certwardenclient/certs:/opt/certwarden/certs
          environment:
            TZ: "Europe/Moscow"
            CW_CLIENT_SERVER_ADDRESS: "https://certwarden.example.com"
            CW_CLIENT_POLL_INTERVAL: "6h"
            CW_CLIENT_0_CERT_NAME: "example.com"
            CW_CLIENT_0_CERT_APIKEY: "MkYMf7eXO8aB9xiNKqwvNVcDGKJ0Dg6v"
            CW_CLIENT_0_KEY_APIKEY: "0UkmZEZK7oieQ6hmz9Fta2obMMZRjAuo"
            CW_CLIENT_0_FILE_UPDATE_TIME_START: "02:00"
            CW_CLIENT_0_FILE_UPDATE_TIME_END: "03:00"
            CW_CLIENT_0_FILE_UPDATE_DAYS_OF_WEEK: "Mon Tue Wed Thu Fri Sat Sun"
            CW_CLIENT_0_RESTART_DOCKER_CONTAINER0: "remnawave-nginx"
            CW_CLIENT_0_CERT_PATH: "/opt/certwarden/certs"
            CW_CLIENT_0_KEY_PEM_FILENAME: "privkey.pem"
            CW_CLIENT_0_CERTCHAIN_PEM_FILENAME: "fullchain.pem"
          logging:
            driver: 'json-file'
            options:
              max-size: '30m'
              max-file: '5'
    ```

    В `CW_CLIENT_0_RESTART_DOCKER_CONTAINER0` указан `remnawave-nginx`. Для панели за Caddy это `remnawave-caddy`.

3. `CW_CLIENT_SERVER_ADDRESS` это адрес сервера Cert Warden, например `https://certwarden.example.com`. Адрес должен начинаться с `https://`, иначе клиент не запустится.

4. `CW_CLIENT_POLL_INTERVAL` задаёт, как часто опрашивать сервер: `30m`, `6h`, `12h` и т. п., но не чаще раза в минуту. Сервер пишет в лог каждый запрос, поэтому слишком короткий интервал его засоряет.

5. `CW_CLIENT_0_CERT_NAME` и `CW_CLIENT_0_CERT_APIKEY` это название и API-ключ сертификата из раздела `Certificates`.

6. `CW_CLIENT_0_KEY_APIKEY` это API-ключ приватного ключа, который использует сертификат (раздел `Private Keys`). Если на сервере переключить сертификат на другой ключ, обновите эту переменную и перезапустите клиент.

7. `CW_CLIENT_0_FILE_UPDATE_TIME_START`, `CW_CLIENT_0_FILE_UPDATE_TIME_END` и `CW_CLIENT_0_FILE_UPDATE_DAYS_OF_WEEK` задают окно, в которое клиент записывает продлённый сертификат и перезапускает контейнеры. Время считается по часовому поясу из `TZ`, без него по UTC.

8. Запускаем клиент:

    ```bash
    cd /opt/certwardenclient && docker compose up -d && docker compose logs -f
    ```

9. В папке `/opt/certwardenclient/certs` должны появиться файлы `fullchain.pem` и `privkey.pem`.

10. Монтируем их в `docker-compose.yml` панели:

    ```bash
    cd /opt/remnawave && nano docker-compose.yml
    ```

    Добавляем в volumes, не забудьте указать ваш домен:

    ```yaml title="docker-compose.yml" "yourdomain.com"
    volumes:
      - /opt/certwardenclient/certs/fullchain.pem:/etc/nginx/ssl/yourdomain.com/fullchain.pem
      - /opt/certwardenclient/certs/privkey.pem:/etc/nginx/ssl/yourdomain.com/privkey.pem
    ```

11. Перезапускаем nginx:

    ```bash
    cd /opt/remnawave && docker compose down remnawave-nginx && docker compose up -d remnawave-nginx
    ```

</Steps>

:::tip[Несколько сертификатов и контейнеров]
Ещё один сертификат добавляется блоком переменных с индексом `1`: `CW_CLIENT_1_CERT_NAME`, `CW_CLIENT_1_CERT_APIKEY`, `CW_CLIENT_1_KEY_APIKEY` и так далее. Задайте ему свои имена файлов (`CW_CLIENT_1_KEY_PEM_FILENAME`, `CW_CLIENT_1_CERTCHAIN_PEM_FILENAME`), чтобы сертификаты не перезаписали друг друга. Дополнительные контейнеры для перезапуска указываются в `CW_CLIENT_0_RESTART_DOCKER_CONTAINER1`, `CW_CLIENT_0_RESTART_DOCKER_CONTAINER2` и так далее, нумерация без пропусков.
:::

## Клиент на сервере ноды Remnawave

:::note
Аналогично ставится и на другие ноды, которые будут получать сертификаты от Cert Warden. Обойтись без клиента можно: на сервере ноды сертификаты умеет выпускать и продлевать сам скрипт (пункт `11` «Управление сертификатами домена» → «Обновить текущие сертификаты»), а при добавлении ноды через меню сертификаты разворачиваются автоматически. Клиент Cert Warden нужен, только если вы хотите раздавать все сертификаты из одного места.
:::

<Steps>

1. Создаём директорию для клиента:

    ```bash
    mkdir -p /opt/certwardenclient/certs && cd /opt/certwardenclient && nano docker-compose.yml
    ```

    Вставляем следующее содержимое:

    ```yaml title="docker-compose.yml" "https://certwarden.example.com" "example.com" "MkYMf7eXO8aB9xiNKqwvNVcDGKJ0Dg6v" "0UkmZEZK7oieQ6hmz9Fta2obMMZRjAuo"
    services:
        certwardenclient:
          image: ghcr.io/mishkatik/certwarden-client:latest
          container_name: certwardenclient
          restart: unless-stopped
          volumes:
            - /var/run/docker.sock:/var/run/docker.sock
            - /opt/certwardenclient/certs:/opt/certwarden/certs
          environment:
            TZ: "Europe/Moscow"
            CW_CLIENT_SERVER_ADDRESS: "https://certwarden.example.com"
            CW_CLIENT_POLL_INTERVAL: "6h"
            CW_CLIENT_0_CERT_NAME: "example.com"
            CW_CLIENT_0_CERT_APIKEY: "MkYMf7eXO8aB9xiNKqwvNVcDGKJ0Dg6v"
            CW_CLIENT_0_KEY_APIKEY: "0UkmZEZK7oieQ6hmz9Fta2obMMZRjAuo"
            CW_CLIENT_0_FILE_UPDATE_TIME_START: "02:00"
            CW_CLIENT_0_FILE_UPDATE_TIME_END: "03:00"
            CW_CLIENT_0_FILE_UPDATE_DAYS_OF_WEEK: "Mon Tue Wed Thu Fri Sat Sun"
            CW_CLIENT_0_RESTART_DOCKER_CONTAINER0: "remnawave-nginx"
            CW_CLIENT_0_CERT_PATH: "/opt/certwarden/certs"
            CW_CLIENT_0_KEY_PEM_FILENAME: "privkey.pem"
            CW_CLIENT_0_CERTCHAIN_PEM_FILENAME: "fullchain.pem"
          logging:
            driver: 'json-file'
            options:
              max-size: '30m'
              max-file: '5'
    ```

2. Переменные заполняем так же, как на сервере панели: `CW_CLIENT_SERVER_ADDRESS` это адрес сервера Cert Warden, `CW_CLIENT_0_CERT_NAME` и `CW_CLIENT_0_CERT_APIKEY` берём из раздела `Certificates`, `CW_CLIENT_0_KEY_APIKEY` из раздела `Private Keys`. Если нода получает другой сертификат, у него в `Post Processing` → `Client` тоже должно быть пусто.

3. Запускаем клиент:

    ```bash
    cd /opt/certwardenclient && docker compose up -d && docker compose logs -f
    ```

4. В папке `/opt/certwardenclient/certs` должны появиться файлы `fullchain.pem` и `privkey.pem`.

5. Монтируем их в `docker-compose.yml` ноды (её веб-сервер тоже называется `remnawave-nginx`):

    ```bash
    cd /opt/remnanode && nano docker-compose.yml
    ```

    ```yaml title="docker-compose.yml" "yourdomain.com"
    volumes:
      - /opt/certwardenclient/certs/fullchain.pem:/etc/nginx/ssl/yourdomain.com/fullchain.pem
      - /opt/certwardenclient/certs/privkey.pem:/etc/nginx/ssl/yourdomain.com/privkey.pem
    ```

6. Перезапускаем nginx ноды:

    ```bash
    cd /opt/remnanode && docker compose down remnawave-nginx && docker compose up -d remnawave-nginx
    ```

</Steps>

## Закрываем доступ к Cert Warden с помощью NetBird

:::note
Если хотите закрыть доступ к Cert Warden с помощью NetBird, следуйте этим шагам.
:::

<Steps>

1. Добавляем сервер Cert Warden в NetBird. Как его установить, написано [здесь](../netbird).

2. В панели управления DNS для домена `certwarden.yourdomain.com` указываем IP-адрес сервера Cert Warden в сети NetBird.

      ![Cert Warden Cloudflare](https://raw.githubusercontent.com/eGamesAPI/remnawave-reverse-proxy/refs/heads/main/docs/src/assets/en/certwarden/certwarden_ip_netbird.png)

3. Теперь, чтобы попасть на страницу Cert Warden, нужно подключиться к вашей сети NetBird через [приложение](https://docs.netbird.io/how-to/installation).

</Steps>

:::caution[Клиенты тоже должны быть в сети NetBird]
Клиент Cert Warden сам обращается к серверу по домену `certwarden.yourdomain.com`. Когда домен указывает на IP в сети NetBird, каждый сервер с клиентом тоже должен быть подключён к NetBird, иначе клиент не сможет забрать сертификат.
:::
