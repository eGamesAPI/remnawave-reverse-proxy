Модуль SSH-доступа позволяет обслуживать второй сервер (например, сервер с нодой) прямо из меню скрипта на панели: обновить пакеты, перезапустить контейнер ноды, посмотреть логи, не открывая вторую SSH-сессию. Другой модуль, [серверный роутинг](/ru/configuration/server-routing/), использует этот доступ автоматически, когда ставит ноду на второй сервер.

- **Пароль спрашивается один раз.** Скрипт установит свой ключ и забудет пароль: на диск он не пишется никогда.
- **Ваш ключ не читается.** Собственный ключ используется по пути, содержимое не копируется и не открывается.
- **Одна строка в `authorized_keys`.** Ключ скрипта живёт отдельной строкой с пометкой `remnawave-reverse-proxy`, ваши строки не трогаются.

Пункт находится в меню скрипта: **4. Расширения ноды → SSH-доступ к удалённому серверу**.

## Первая настройка

Скрипт сам предложит самый простой путь:

<Steps>

1. **Проба существующих ключей.** Если на этом сервере уже есть ключ, который открывает второй сервер, скрипт молча возьмёт его: вопросы не задаются, на удалённом сервере ничего не меняется.
2. **Указать свой ключ.** Если ключ лежит здесь, но не нашёлся автоматически, можно указать путь до него.
3. **Пароль root один раз.** Скрипт спросит пароль (ввод скрыт), установит свой отдельный ключ и забудет его.
4. **Ручная вставка.** Для серверов с закрытым парольным входом скрипт покажет свой публичный ключ и команду, которую нужно выполнить на втором сервере. Проверка результата повторяется по <Kbd windows="Enter" />, выход из ожидания клавишей <Kbd windows="Q" />.

</Steps>

:::tip[Проверка после настройки]
Модуль сразу предлагает проверить соединение и показать hostname удалённого сервера. Если увидели его, доступ работает.
:::

## Несколько серверов

Серверов может быть сколько угодно. Список выглядит так:

```
SSH-доступ к удалённому серверу

 Настроено серверов: 2

 1. root@203.0.113.20:22 (Kazan)
 2. root@203.0.113.5:22 (Frankfurt)

 3. Настроить новый сервер

 0. Выход
```

При настройке можно задать каждому серверу название: оно отображается в скобках рядом с адресом и переименовывается в любой момент. Ключ у всех серверов один (панель = одна точка доступа), но на каждом сервере своя строка в `authorized_keys`.

## Выполнение команд

Пункт «Выполнить команду» в меню сервера запускает команду на удалённом сервере, вывод приходит в терминал, в конце скрипт покажет код завершения. Типовые сценарии:

```bash title="Обновление пакетов на удалённом сервере"
apt update && apt upgrade -y
```

```bash title="Обновление ноды (команды стартуют в /root, compose нужен cd)"
cd /opt/remnanode && docker compose pull && docker compose up -d
```

```bash title="Логи ноды"
docker logs remnanode --tail 50
```

:::note[Ограничения]
Интерактивные программы (`top`, `nano`, `mc`) не заработают: терминал на удалённую сторону не выделяется. Для просмотра состояния используйте обычные команды с текстовым выводом: `docker logs`, `free -h`, `df -h`.
:::

<details>
<summary><strong>Под капотом: где это хранится</strong></summary>

Все данные доступа лежат на панели в `/usr/local/remnawave_reverse`:

<FileTree>
- /usr/local/remnawave_reverse
  - remote-exec
    - **203.0.113.20_22.target** (сервер: адрес, порт, пользователь, ключ, название)
    - 203.0.113.5_22.target
  - remote-exec.active (какой сервер использовался последним)
  - ssh
    - id_ed25519 (ключ скрипта, один на все серверы)
    - known_hosts
</FileTree>

Файлы `.target` обычные `key=value`, правятся вручную только в крайнем случае: меню переименования и перенастройки делает то же самое безопаснее.

</details>

## Отзыв доступа

Пункт «Отозвать доступ» удаляет строку скрипта из `authorized_keys` на удалённом сервере, стирает локальный ключ (если им больше никто не пользуется) и забывает сервер. Ваш собственный доступ к серверу при этом не меняется никак.
